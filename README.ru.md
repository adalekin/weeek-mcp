## Зачем это

У [Weeek](https://weeek.net) есть API для задач, но нет публичного API у базы знаний — а именно там живут регламенты, спеки и roadmap'ы. `weeek-mcp` закрывает обе половины:

- **Задачи — через официальный REST API.** Создать, перекинуть по колонкам, назначить исполнителя, проставить приоритет и кастомные поля, залогировать время, оставить комментарий — всё из чата.
- **База знаний — там, где публичного API нет.** Сервер говорит с внутренним API Weeek и его совместным редактором напрямую, поэтому умеет не только читать, но и **править тело документов на месте** — заголовки, списки, таблицы. Документы сами превращаются в Markdown и обратно.
- **База знаний как контекст Claude.** Каждый документ отдаётся как MCP-**ресурс**: вы подтягиваете в диалог **содержимое** документа, а не ссылку на него.

Больше не нужно дёргать API руками, копировать текст из веб-интерфейса и скакать по вкладкам: вы описываете, что нужно, словами, а остальное делает Claude.

## Что умеет

### Задачи и доски

Публичный REST API.

- Проекты, доски, колонки, полный жизненный цикл задачи: создание, обновление, завершение, перенос между колонками, исполнители и наблюдатели.
- Приоритеты (числом или меткой), кастомные поля по имени, таймер и учёт времени, вложения.
- Комментарии: добавить, переписать на месте, удалить. У публичного API Weeek комментариев нет вовсе — сервер делает это через веб-API на сохранённой сессии, браузер при этом не запускается.
- Администрирование воркспейса: теги, проекты, доски, колонки, портфели, кастомные поля.

### База знаний

Внутренний API плюс совместный редактор.

- Поиск, список, чтение, создание, переименование, удаление документов.
- **Редактирование содержимого на месте.** Тело документа хранится в общем совместном документе (Hocuspocus/Yjs), которого REST отдаёт только снимок, поэтому сервер пишет прямо в этот канал, сохраняя id документа.
- Таблицы с настройкой ширины колонок и иконки документов (эмодзи или встроенные иконки Weeek).

### Умное поведение

Инструменты появляются под то, что настроено: задачи — когда задан API-токен, база знаний — когда есть логин или сохранённая сессия. Список инструментов не захламляется тем, чем вы не пользуетесь.

## Требования

- Python 3.10+
- **API-токен Weeek** для работы с задачами (Weeek → Настройки → API).
- Для базы знаний: `weeek-mcp[kb]` плюс Chromium (нужен только для входа) и либо логин/пароль, либо сессия, засеянная один раз через `weeek-mcp-login`.

## Установка

```bash
pip install weeek-mcp              # только задачи
pip install "weeek-mcp[kb]"        # + база знаний
playwright install chromium         # рантайм для KB
```

Через [uv](https://docs.astral.sh/uv/) в своём проекте:

```bash
uv add "weeek-mcp[kb]"
```

Пошаговое подключение к Claude Desktop и Claude Code — в **[docs/claude.md](docs/claude.md)**.

## Настройка

Переменные окружения (или скопируйте `.env.example` в `.env`). Можно включить только задачи, только базу знаний или всё сразу.

| Переменная | Зачем |
| --- | --- |
| `WEEEK_API_TOKEN` | Токен API задач. Обязателен для инструментов задач. |
| `WEEEK_EMAIL` / `WEEEK_PASSWORD` | Первый автоматический вход в KB. Необязательны (при 2FA/SSO используйте `weeek-mcp-login`). |
| `WEEEK_WORKSPACE_ID` | ID воркспейса KB. Необязательно — определяется автоматически через `/ws`. |
| `WEEEK_STORAGE_STATE` | Куда кешируется сессия браузера (по умолчанию — под `~/.local/state`). |
| `WEEEK_HEADLESS` | `false`, чтобы видеть браузер во время входа. |
| `WEEEK_KB_CACHE_TTL` | Сколько секунд кешировать список документов KB (по умолчанию `300`). |
| `WEEEK_DEBUG_LOG` | `1`/`true` — писать диагностические логи с таймингами в `~/.local/state/weeek-mcp/debug.log` (некоторые клиенты глотают stderr). По умолчанию выключено. |

### Первый вход в базу знаний

Если у аккаунта есть 2FA или капча, автоматический вход не сработает. Засейте сессию один раз, вручную — команда откроет браузер, вы входите, после чего сессия кешируется для headless-переиспользования:

```bash
weeek-mcp-login
```

## Запуск

Сервер работает по stdio:

```bash
weeek-mcp
```

### Claude Desktop

Добавьте в `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "weeek": {
      "command": "weeek-mcp",
      "env": {
        "WEEEK_API_TOKEN": "...",
        "WEEEK_STORAGE_STATE": "/абсолютный/путь/до/storage_state.json"
      }
    }
  }
}
```

Настройка Claude Code (`claude mcp add`) и разбор частых проблем — в [docs/claude.md](docs/claude.md).

### Другие MCP-клиенты

`weeek-mcp` — обычный stdio-сервер, поэтому подойдёт любому MCP-клиенту, который запускает серверы как локальный подпроцесс: Cursor, Windsurf, Cline, Continue, Zed, VS Code (Copilot в agent mode), Gemini CLI, Goose, LibreChat и другим, а также вашим собственным агентам на MCP SDK. Команда и переменные те же, что выше, — меняются только формат и расположение конфига.

Cursor (`~/.cursor/mcp.json` или `.cursor/mcp.json` в проекте) использует ту же форму, что и Claude Desktop:

```json
{
  "mcpServers": {
    "weeek": {
      "command": "weeek-mcp",
      "env": { "WEEEK_API_TOKEN": "..." }
    }
  }
}
```

VS Code (`.vscode/mcp.json`) — ключ `servers` и явный `type`:

```json
{
  "servers": {
    "weeek": {
      "type": "stdio",
      "command": "weeek-mcp",
      "env": { "WEEEK_API_TOKEN": "..." }
    }
  }
}
```

> **Про базу знаний.** Задачные инструменты и `weeek_kb_*` — обычные MCP-tools и работают почти везде. А подтягивание документов через меню вложений опирается на MCP-**Resources**, которые выводят наружу не все клиенты. Где их нет, читайте KB через `weeek_kb_read`/`weeek_kb_search` — содержимое всё равно попадёт в контекст. Наличие поддержки MCP и resources у конкретного клиента меняется быстро; перед настройкой свериться стоит с его документацией.

## Инструменты

### Задачи

| Группа | Инструменты |
| --- | --- |
| Чтение и навигация | `weeek_whoami`, `weeek_list_members`, `weeek_list_projects`, `weeek_list_boards`, `weeek_list_board_columns`, `weeek_list_tasks`, `weeek_get_task` |
| Жизненный цикл задачи | `weeek_create_task`, `weeek_update_task`, `weeek_complete_task`, `weeek_uncomplete_task`, `weeek_delete_task`, `weeek_move_task` |
| Исполнители, наблюдатели, иерархия | `weeek_set_assignees`, `weeek_remove_assignees`, `weeek_set_watchers`, `weeek_remove_watchers`, `weeek_set_task_parent`, `weeek_add_task_to_project`, `weeek_remove_task_from_project` |
| Время и вложения | `weeek_task_timer`, `weeek_manage_time_entry`, `weeek_upload_attachment`, `weeek_get_attachment` |
| Поля и комментарии | `weeek_list_custom_fields`, `weeek_list_task_comments`, `weeek_add_task_comment`, `weeek_update_task_comment`, `weeek_delete_task_comment` |

### Администрирование воркспейса

`weeek_manage_tags`, `weeek_manage_projects`, `weeek_manage_boards`, `weeek_manage_board_columns`, `weeek_manage_portfolios`, `weeek_manage_custom_fields`.

Каждый берёт `action` (create/update/delete/…), а не отдельный инструмент под каждую операцию — CRUD регулярный, а список инструментов остаётся читаемым. Кастомные поля живут на уровне доски, проекта или всего воркспейса, поэтому этот инструмент берёт `scope` (`global`/`project`/`board`) плюс `scope_id`.

### База знаний

| Группа | Инструменты |
| --- | --- |
| Чтение | `weeek_kb_search`, `weeek_kb_list`, `weeek_kb_read` |
| Запись | `weeek_kb_create`, `weeek_kb_update`, `weeek_kb_delete` |
| Оформление | `weeek_kb_table_widths`, `weeek_kb_icons` |

> `weeek_kb_update` с новым содержимым пишет в общий Yjs-документ через совместный websocket Weeek, потому что тела сохраняются именно там, а не в REST. Браузер не участвует, id документа сохраняется.

### Как это ведёт себя

**Приоритеты.** Принимаются либо числом Weeek, либо меткой:

| Число | Метка |
| --- | --- |
| `0` | Низкий |
| `1` | Средний |
| `2` | Высокий |
| `3` | Замороженный |

**Кастомные поля.** Задаются через `custom_fields`: у существующей задачи — по имени или id поля (`{"Ссылка на фичу": "https://…"}`, `null` очищает поле, для select подходит имя или id опции), в `weeek_create_task` — только по id; список полей даёт `weeek_list_custom_fields`. Поле принадлежит тем проектам, куда его добавили, и Weeek ничего не сохраняет при записи в поле вне этого набора — поэтому запись проверяется и результат сообщается.

**Описания задач.** Редактируются у существующей задачи: `weeek_update_task` принимает `description` как Markdown (пустая строка очищает). REST API Weeek принимает описание только при создании — у `PUT /tm/tasks/{id}` такого поля нет, — потому что описания синхронизируются через тот же совместный канал, что и тела документов KB; эта запись идёт в тот канал и требует сессии базы знаний. `weeek_create_task` по-прежнему принимает `description` как HTML — именно это хранит тот эндпоинт.

**Комментарии.** Читаются через `weeek_list_task_comments`, пишутся через `weeek_add_task_comment` и переписываются на месте через `weeek_update_task_comment` (всё в Markdown) — исправленный комментарий лучше, чем поправка отдельным сообщением под исходным. `weeek_delete_task_comment` удаляет комментарий насовсем; корзины для комментариев Weeek не держит. У публичного API Weeek комментариев нет вовсе, поэтому они идут через веб-API на сессии базы знаний; браузер не запускается, используются только сохранённые cookie.

**Таблицы в KB.** Ширина колонок — единственный размер, который нужно задавать (минимум 90 px). Новые таблицы подгоняются под ширину контентной колонки документа (~676 px) вместо дефолтных 180 px на колонку у Weeek, а существующая ширина переносится через `weeek_kb_update` — таблица, у которой прибавилась или убавилась колонка, подгоняется заново. `weeek_kb_table_widths` задаёт ширины явно: `widths: [300, 200, 176]` для точных размеров или `fit: true`, чтобы растянуть таблицу на контентную колонку.

**Иконки документов.** Передайте `icon` в `weeek_kb_create`/`weeek_kb_update` как одно эмодзи (`🚀`) или как имя одной из встроенных иконок Weeek (`weeek_kb_icons` их перечисляет); пустой `icon` убирает иконку. В списках показывается текущая иконка документа.

## База знаний в контексте Claude

Каждый документ публикуется как MCP-ресурс (`weeek-kb://<id>`). В Claude Desktop его добавляют из меню вложений (**+**) подключённого сервера — можно листать список или сузить его через `weeek_kb_search`, — и клиент подтягивает **содержимое документа, а не ссылку**.

> **О панели Context в проекте.** Claude Desktop показывает MCP-ресурсы как вложения. Останется ли выбранный ресурс в панели *Context* проекта (а не только в одном диалоге) — зависит от версии Claude Desktop. Поведение «контент, а не ссылка» работает в любом случае.

## Статус и ограничения

- **Инструменты задач** следуют опубликованной OpenAPI-спецификации Weeek.
- **База знаний** использует **внутренний, недокументированный** API Weeek (`/ws/{id}/kb/...`). На него нет гарантий стабильности, он может измениться без предупреждения; если вызовы KB начнут падать, эндпоинты стоит смотреть в [`weeek_mcp/kb/client.py`](weeek_mcp/kb/client.py). Автовход рассчитан на двухшаговую веб-форму Weeek ([`weeek_mcp/kb/session.py`](weeek_mcp/kb/session.py)); аккаунтам с 2FA/капчей/SSO нужно засеять сессию через `weeek-mcp-login`.
- Содержимое документов — это ProseMirror/TipTap JSON, который конвертируется в Markdown и обратно ([`weeek_mcp/kb/prosemirror.py`](weeek_mcp/kb/prosemirror.py)). Редактирование существующего тела идёт через совместный канал Weeek (записи содержимого по REST нет): [`weeek_mcp/kb/collab.py`](weeek_mcp/kb/collab.py) говорит по протоколу Hocuspocus, аутентифицируется по разовому тикету на сокет и заменяет фрагмент `prosemirror` в Y.Doc документа. Авторинг покрывает основной набор Markdown (заголовки, абзацы, списки, жирный/инлайн-код, блоки кода, цитаты, разделители); сложные случаи вроде вложенных списков и таблиц упрощаются.
- Ширина колонок таблицы живёт на узле `table_body` как строка JSON и пишется вместе с телом, а не после него ([`weeek_mcp/kb/tables.py`](weeek_mcp/kb/tables.py)). Цвета ячеек и колонок хранятся рядом с ширинами, но инструментами пока не выведены наружу.
